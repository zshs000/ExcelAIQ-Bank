# “可以接受误差”之后，我漏问了什么？

今天聊限流时，我又被自己几个月前的理由说服了。

我的项目流量不大，验证码发送限流主要用来防刷。假设额度是 100，就算并发时略微超出，只要能挡住后面大量重复请求，这个设计就有价值。我本来就允许一定误差，为什么非得用 Lua？

但顺着代码往下讨论，我又发现：在当前 Redis 部署条件下，把相关检查和更新合成一个短脚本，工作量并没有想象中那么大。

那为什么不改？

我居然能同时认可这两个选择。这次讨论真正让我记住的，就是这个看起来很矛盾的地方。

**最后我的决定是改：用 Lua 合并发送资格检查、验证码创建和日计数更新。** 但我更想记下来的，是自己为什么绕了一圈，才走到这个决定。

---

先把这次讨论的代码范围说清楚。

验证码发送有两个日额度：手机号每天 10 次，IP 每天 50 次。除此之外，同一手机号、同一场景下，如果已有验证码，就拒绝重复创建。

原来的主要顺序是：

```text
检查手机号日额度
检查 IP 日额度
尝试创建验证码，已有则拒绝
创建成功后，手机号和 IP 日计数分别加一
首次创建日计数时，设置当天结束过期
```

把计数放在后面，能让普通的重复发送请求被拒绝后不占用日额度。但前面的额度检查没有同时占住名额，其他请求仍可能读到旧数字。

例如，某个 IP 的日计数已经是 49，两个不同手机号的请求都在计数更新前通过了检查，又各自成功创建验证码，最终就会记到 51。

这里的 `INCR` 并没有算错。问题在于，请求是否允许继续，是根据此前读到的 49 决定的。

同一手机号、同一场景的普通并发，则会受到验证码 `setIfAbsent` 的约束：只要这个 key 在竞争期间一直存在，后续创建就会被挡住。所以不能笼统地把所有并发都算成超放，也不能说超放必定只有三五次。

讨论中，AI 一度把它解释成一个取舍：创建成功才记账，可以避免拒绝请求扣额度，但要接受并发误差。

我追问了一句：**这个取舍是一定的吗，难道没有兼得的方式？**

有。把这组 Redis 操作放在同一个短脚本里即可：

```text
检查额度、检查验证码是否存在
    ├─ 任一业务检查不通过：返回拒绝，不写入、不扣额度
    └─ 全部通过：创建验证码、更新计数、设置过期时间
```

脚本执行期间，其他请求不能插进来。一个请求使用了最后一份额度，下一个请求再检查时，就会看到更新后的数字。

这解决的是 Redis 内部的竞争。脚本本身仍要先检查再写入，因为 Lua 运行出错时，Redis 不会自动回滚前面已经完成的写操作。

而短信是否最终送达，是另一件事，不在这个原子操作里。

---

为什么我认为这次值得改？不能只用“脚本很短”四个字带过去。

把改动摊开，范围其实很明确：

| 方面 | 具体变化 |
|---|---|
| Redis 操作 | 将额度读取、验证码条件写入、计数递增与首次过期设置集中到一个脚本里 |
| Java 调用 | 传入相关 key、额度、验证码和过期参数，根据脚本返回结果转换为原有业务响应 |
| 验证工作 | 覆盖同 IP 多手机号、同手机号不同验证码场景的竞争，以及业务拒绝不扣额度、首次计数有过期时间等行为 |
| 部署 | 继续使用当前不分片的 Redis，不增加服务或协调组件 |

这里增加了脚本和返回结果的维护责任，也需要验证行为。但手机号额度、共享 IP 额度、验证码和日计数这些状态，本来就存在。

我不需要为这次改造增加一套新的业务状态机。它的收益也具体：消除检查与记账之间的并发间隙，同时保留业务检查拒绝不扣额度的规则。

这就是我的成本判断依据。

如果使用 Redis Cluster，事情会不同：同一脚本涉及的 key 需要在同一个哈希槽。手机号额度和跨手机号共享的 IP 额度怎么放，要重新设计。集中到同一槽可以保留原子操作，但会集中这部分负载；按手机号拆出多份 IP 额度，则改变了业务规则。

我的学生项目没有这个分片要求。这是未来改变部署时需要重新评估的条件，不是当前改造的阻碍。

---

真正让我意外的是：我并非刚刚才知道 Lua。

在三四月写的[《这两天我被验证码登录狠狠上了一课》](这两天我被验证码登录狠狠上了一课.md)里，我已经用它解决了验证码的原子消费。

随后，我继续追问：验证码消费了，下游用户服务失败或超时怎么办？是不是应该先锁住验证码，成功再删除，失败就释放？

这个想法引出了更多状态：谁持有、什么时候释放、中途挂了怎么恢复、重复请求怎么处理。我后来想到用 `login_ticket` 保存“验证已通过、登录尚未完成”这件事，把后续流程从验证码身上分出来。

但我最终决定，当时先不引入它。旧文里写的是：

> 系统设计不是“我能不能想到更强的方案”，而是“我该不该现在就付出这部分复杂度”。

这段判断有具体依据：ticket 确实需要新的状态和恢复流程。

而文章到了发送限流，重点变成了论证误差可以接受。最后总结时，我又写下：

> 强一致只留给真正需要强一致的地方。

今天回看，我开始怀疑，那个“只”字是不是把选择收得太窄了。

业务允许误差，说明我可以采用近似方案；它并没有排除另一种可能：做准确也很便宜，因此仍然值得选。

我已经记不清当时每一步怎么想的。但从旧文能看到，我充分解释了为什么不必追求严格，却没有单独比较发送限流改成 Lua 的实际成本。

**前面“增强保证需要付出复杂度”的经验，可能被我直接带到了后面。** 可一个短脚本和一套跨服务恢复协议，并不是同一档投入。

---

我很喜欢联系不同的知识，这件事在之前几篇文章里特别明显。

在[《从存 URL 到存 objectKey》](从存URL到存objectKey.md)里，我把对象身份、outbox 和 `login_ticket` 放在一起理解；在[《从 importQuestions 到分阶段导入协议》](从importQuestions到分阶段导入协议.md)里，我又用“复杂度应该放在哪里”解释 batch、chunk、临时表和事务边界。

这些联系确实帮我建立了一张网。实习几个月，一直在做具体业务，很多细节已经有点模糊，但今天聊到“短信发送失败要不要退额度”时，我马上想起了验证码消费后的下游超时。

那种直觉很真实：前一步已经发生，后一步的失败究竟意味着什么？哪些结果明确失败，哪些只是暂时不知道？应该恢复旧资源，还是由另一份状态承接重试？

没有之前的思考，我未必能这么快问到这里。

所以我仍然喜欢这种学习方式。只是今天发现，它也可能让我太快抵达一个熟悉的结论：这是复杂度问题，业务允许保留缺口，我们接受，讨论结束。

框架帮助我认出了问题的结构，却可能跳过了当前方案的具体比较。

而且，复杂度也不总是只能原样转移。分散的 Redis 操作带来许多执行交错，把它们合并后，一部分需要推理的情况就消除了。不能因为恢复链路很复杂，就预设所有增强正确性的改造都很复杂。

**这次需要补上的，是从框架回到操作本身的那一步。**

---

可即使想到了这里，我还是忍不住替原方案辩护：它本来就能满足当前的基本防刷目标，我也没有要求精确，不改有什么错？

这就是开头那个把我绕住的问题。

后来聊明白了：我评价两个方案时，问的根本不是同一件事。

“原方案可以接受”，回答的是它够不够用。

“Lua 值得采用”，回答的是额外付出与额外收益是否合算。

两者可以同时成立。原方案达到要求，不会自动证明改进不值得；今天决定改，也不需要先证明过去的方案一无是处。

对当前项目，我选择把 Redis 内的发送资格检查和记账合起来。至于短信发送失败退额度、验证码消费后恢复登录流程，我仍然选择暂时不做。这些决定各有自己的成本依据，不能由其中一个代替其他几个。

写下这层区别，也让我想到最近在看的架构腐化：当年的局部选择可能成立，后来条件变了，实现却被继续复制。文档应该留下当时的理由和重评条件，测试应该守住明确的行为约定。比如这次，Redis 是否分片，就是一项需要留给后来人的前提。

我想保留旧文里“允许近似”的认识，也想给以后的自己补一句提醒：

> 现状可以接受。那最小改法是什么，实际需要多付出什么？

问过以后仍然决定不做，有依据。发现很便宜，决定改，也有依据。

这次我选择改。
